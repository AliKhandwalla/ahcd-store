# Deployment

Everything needed to run AHCD in production, across four services. No credential values
appear in this file. Every secret is generated by the operator and stored only in the
hosting provider's environment settings.

| Service | Role |
| --- | --- |
| **Vercel** | Hosts the Next.js application; builds from `main` |
| **Supabase** | Postgres, Row Level Security, Google authentication, private Storage |
| **Cloudflare** | DNS for the apex domain, plus inbound Email Routing |
| **Resend** | Outbound transactional email on a sending subdomain |

---

## Environment variables

| Variable | Exposed to browser | Purpose |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Yes | Supabase project URL |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Yes | Supabase publishable key |
| `NEXT_PUBLIC_SITE_URL` | Yes | Public origin used to build confirmation links. Must be the live origin in production |
| `ADMIN_EMAIL` | **No** | The email address permitted to access `/admin` |
| `RESEND_API_KEY` | **No** | Resend key with `sending_access`. Sends confirmation and admin test email |
| `RESEND_FROM_EMAIL` | **No** | Verified sending identity, e.g. `Brand <newsletter@mail.example.com>` |
| `RESEND_REPLY_TO` | **No** | Reply address, also published in the privacy notice |
| `RESEND_CONTACTS_API_KEY` | **No** | Resend key with `full_access`. Required for subscriber management |
| `NEWSLETTER_ENABLED` | **No** | Master switch, **fail closed**. Signups are off unless this is `true`, `1`, `yes` or `on` |
| `NEWSLETTER_RPC_SECRET` | **No** | Binds the signup database function to this server. Without it, signups stay closed |

Set every variable in Vercel for **Production, Preview and Development**. Vercel scopes
variables per environment, and one present in a single environment but missing from
another produces failures that look like application bugs.

The two `NEXT_PUBLIC_` values are compiled into the client bundle by design. The
publishable key is intended to be public; access control is enforced by Row Level
Security, not by concealing it. Nothing else may carry that prefix.

**No Supabase secret or service-role key is used anywhere in this project.**

See [`.env.example`](.env.example) for a template, and the
[README](README.md#why-the-newsletter-needs-two-resend-keys) for why the newsletter needs
two Resend keys.

## Supabase

### Database

In the Supabase dashboard, open **SQL Editor** and run
[`supabase/schema.sql`](supabase/schema.sql). It is idempotent and safe to re-run: on an
empty project it reproduces the production schema in full, and on an existing one it is a
no-op.

An existing database instead takes the files in
[`supabase/migrations/`](supabase/migrations) in filename order. These are additive and
idempotent.

> **`schema.sql` hard-codes the administrator's email** inside `is_ahcd_admin()`. It must
> match `ADMIN_EMAIL` exactly. If you are adapting this project, change it there before
> running the file — and be aware that re-running the file with a different address will
> revoke the previous administrator's access.

#### Planned improvement: move the administrator email out of the schema

The address sits in a tracked file in a public repository. It is an identifier, not a
credential — knowing it grants nothing, because authorisation still requires a verified
Google session for that account — so there is nothing to rotate and no urgency. But it is
a personal address in public, and it does not need to be.

The intended fix is to store it in the `app_config` table, the same place the newsletter
signup secret's hash already lives, and have `is_ahcd_admin()` read from there:

```sql
-- Sketch only; not yet implemented.
create or replace function public.is_ahcd_admin()
returns boolean language sql stable security definer
set search_path = public, pg_temp
as $$
  select lower(coalesce(auth.jwt() ->> 'email', '')) =
         (select lower(value) from public.app_config where key = 'admin_email');
$$;
```

This was **deliberately not done for v1.0.0**. `schema.sql` is documented as safe to
re-run, and a version that reads from a table would lock the administrator out of their
own dashboard if the file were ever re-run before the `app_config` row existed. The change
needs its own migration, applied in the right order, and verification with a live admin
session — which is a change to working functionality, not release preparation.

Note that the current address remains in Git history regardless, so this reduces future
exposure rather than undoing past exposure.

Then generate the newsletter signup secret, which is deliberately in neither file:

```bash
npm run newsletter:secret
```

It prints two things: a secret for `NEWSLETTER_RPC_SECRET` in the server environment, and
a SQL statement storing only that secret's **hash** in `app_config`. Apply both halves.
The hash cannot be reversed and is not a credential. Until both are in place the signup
function refuses every call and the form reports that signups are not open — the intended
fail-closed behaviour, not a fault.

### Authentication

Under **Authentication → URL Configuration**:

- **Site URL** must be the canonical production origin. This is where Supabase sends
  users when it has no valid redirect target, including OAuth error paths, so a stale
  value silently routes people to the wrong host.
- **Redirect URLs** must list every origin the app is served from — local development,
  the Vercel domain, the custom domain — and nothing else. This list is what stops a
  caller supplying their own callback.

In Google Cloud, the authorised redirect URI points at **Supabase**, not at this
application, so it does not change when the site's domain changes.

### Storage

Two private buckets, `update-images` and `product-images`. Neither is public. Images are
served through short-lived signed URLs, and through stable `/og/...` proxy routes wherever
a durable public URL is needed — a signed URL expires within the hour, which is useless in
an email or a social card.

## Vercel

The application deploys automatically when `main` is updated. Add every environment
variable before the first deployment; they are read at build time, so a deployment created
before they existed must be rebuilt.

### Promoting a build

New commits do **not** promote themselves to production on this project. After a push,
open the deployment under **Deployments** and choose **Promote to Production**.

The *Redeploy* button rebuilds the deployment it is attached to — the previous commit —
which produces a green build while production still serves old code.

Vercel builds the tip of a push, so several commits pushed together produce one
deployment. An earlier commit having no deployment row of its own is normal.

After promoting, confirm which build is live using a behaviour unique to the new commit,
rather than trusting the deployment list.

## Cloudflare

DNS for the apex domain:

- **A / CNAME** records point at Vercel. `www` redirects permanently to the apex.
- **MX** records point at Cloudflare Email Routing, which forwards inbound mail to a real
  inbox. This coexists with Resend because Resend sends from a **subdomain**, so the two
  never contend for the same records.
- Records used by Resend must be **DNS only (proxy off)**. Proxied records fail
  verification.

## Resend

Sending is configured on a `mail.` subdomain rather than the apex, which leaves the apex
free for inbound routing.

Two things must exist in Resend before signups work, and neither is obvious:

1. **Contact properties must be predefined.** `consent_version`, `consented_at`,
   `confirmed_at` and `source` have to be created under contact properties, or every
   confirmation fails with a 422.
2. **A `User-Agent` header is required** on API calls, or Resend returns 403. The client
   sets one.

The admin area has an on-demand **Check configuration** button that verifies the contacts
key really has full access and that all four properties exist. It makes live calls only
when clicked — never on render, build or deploy.

### Deliverability

SPF, DKIM and DMARC are all configured. The DMARC record at `_dmarc` publishes
`v=DMARC1; p=none;`, which is the correct starting policy: receivers report on
authentication failures without any mail being quarantined or rejected while the setup is
still being observed.

Two refinements worth making later, in this order:

1. **Add a `rua=` reporting address.** Without one, `p=none` publishes a policy but
   collects no aggregate reports, so the monitoring the policy exists to enable is not
   actually happening.
2. **Tighten to `p=quarantine`, then `p=reject`,** once those reports show all legitimate
   mail passing. Do not tighten before that — forwarded mail is the usual casualty, and
   this domain already forwards through Cloudflare Email Routing.

The `mail.` sending subdomain publishes no record of its own and therefore inherits the
apex policy.

## Release checklist

```bash
npm run typecheck && npm run lint && npm run build && npm test
```

1. Commit and push to `main`
2. Wait for the Vercel build, then **Promote to Production**
3. Confirm the new build is actually live
4. Run the smoke suite against production:

```bash
SMOKE_BASE_URL=https://alisheatcrunchdelight.com npm test
```

### Ordering migrations against deploys

**Order matters when a migration and a deploy depend on each other.** A migration that
drops a function the live code still calls, or repoints paths at files the live build does
not yet contain, breaks production in the window before the deploy lands. Both have
happened on this project.

Apply the migration and promote the build together, and switch the affected public feature
off while doing it.
